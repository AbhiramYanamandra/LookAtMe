## Overview

The brief was an election-centre server. Districts send in incremental vote records over a network nobody trusts. Each record carries a **district ID, a candidate ID, a vote count, and a tag**. The server regenerates the tag from the record using a shared secret key, throws away any record whose tag doesn't match, and adds the rest to a live table of per-candidate and per-district totals.

We built that as a custom **five-stage pipelined processor** in VHDL, starting from a classic IF / ID / EX / MEM / WB core. The team of six split into three pairs: decoder, memory and processor. I was on the processor pair, and I wrote the simulation analysis.

## One record, three instructions

The processor runs a small custom instruction set. Each incoming record is processed as three instructions issued back to back:

- **SEC** loads the secret key into the key register.
- **BNE** compares the record's tag with the one the decoder regenerates.
- **WRITE** adds the vote count to tally memory.

**CAND** and **DIST** read totals back out. In the board build a record is 12 bits (an 8-bit vote count, a 2-bit district and a 2-bit candidate) plus a 4-bit tag. All of these widths are generics, so the same design scales to larger elections.

## What each stage does

- **IF.** The opcode, the record, its tag and the secret key are latched into IF/ID together. The record then travels with its instruction through every pipeline register, so there is no separate data path to keep in sync.
- **ID.** The control unit decodes the opcode into `sec_enable`, `bne_enable` and a two-bit tally-memory `mode`.
- **EX.** The ALU and register comparison from the base core stay in place for ordinary instructions. Tally instructions pass straight through.
- **MEM.** All the real work happens here. The key register loads when SEC arrives. A combinational **decoder** splits the record into blocks, then flips, swaps, shifts and XORs them under the key to regenerate the tag. A comparator checks that tag against the one that came with the record. **Tally memory** updates three cells on a single clock edge: the candidate-in-district entry, the candidate's total and the district's total.
- **WB.** Unused by tally instructions, which retire in MEM.

The forwarding unit and hazard detection from the base design are kept for register-to-register instructions. Forwarding routes results from MEM and WB back into EX, and the hazard unit stalls and inserts bubbles where a value isn't ready yet.

## What re-simulating it showed

Running the core cycle by cycle for this page turned up something the original testing missed.

The tag check doesn't resolve until the cycle after BNE reaches MEM. By then, WRITE has already moved up behind it into MEM. When the tags don't match, `sig_flush` goes high, but the flush clears the **IF/ID** register, which is empty. So the tampered record's vote is written to tally memory anyway. Choose *Tampered tag* above: the tally goes from 1 to 2.

The fix is one line. It forces tally memory's mode to idle in the same cycle the tag check fails:

```vhdl
sig_tally_mode_gated <= "11" when sig_tag_flush = '1' else sig_tally_mode_MEM;
```

With that gate in place, the same simulation drops the tampered write and leaves the valid record's behaviour unchanged (*With fix* above). The general lesson: a flush only helps if it reaches the stage that commits. Here the commit happens in MEM, not at the front of the pipeline.

## On hardware

The design is synthesised in **Vivado** and runs on a **Basys-3 (Artix-7)**. The centre button sends a record, the switches set the record and tag, and the direction buttons show each candidate's total on the seven-segment display.

It is small: **334 LUTs (1.61%)** and **393 flip-flops (0.94%)**. The binding constraint is I/O, at **49 pins (46.23%)**: this is a processor whose cost is dominated by talking to the outside world rather than by computing. Timing closes at 100 MHz with **1.819 ns of worst negative slack**, which puts the maximum clock at about **122 MHz**. The critical path runs from the EX/MEM register through the decoder into tally memory, the same stage that does all the work.

## What I'd change

The decoder and comparator are pure combinational logic, so they don't need to be in the pipeline at all. If you check the tag *before* the processor and only issue WRITE when it matches, the processor becomes a plain read/write interface to tally memory. That shortens the critical path and makes the late-flush bug impossible by construction. For a national-scale election, the next steps would be caching the frequently hit tally entries and issuing independent records in parallel.
